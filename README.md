# CodeAtlas

Semantic search over four of my own projects, and an evaluation harness that
measures how well it works.

The retrieval part is small: Tree-sitter chunking, BM25, MiniLM embeddings,
Reciprocal Rank Fusion, a per-file cap. The reason the repository exists is the
measurement: 36 questions with labelled answer files, three chunkers and six
retrieval strategies scored on them, a 95% confidence interval on every number,
and a paired comparison behind every sentence that says one thing beat another.

Every table in this file is rendered from `results/` by
`codeatlas render-docs`, and CI fails if the tables and the JSON disagree. The
corpus is pinned by commit and file hash, so the numbers can be regenerated by
anyone (see [Running it](#running-it)).

## The corpus

Four repositories, checked out at fixed commits. `results/corpus_manifest.json`
lists every indexed file with its line count and sha256, and the evaluator
refuses to run on a directory that differs from it.

Files are Python, Java, JavaScript, Markdown and YAML, plus two
`requirements.txt` files. Tree-sitter parses the Python and Java files and
Markdown splits on its headings; everything else is chunked by windows in all
three chunkings.

## The questions

36 questions I wrote against these projects, phrased the way someone new to a
repository would ask ("what stops the relays flickering when my hand shakes
slightly"), never by pasting identifiers, each with every file that answers it.
They are frozen in `eval/golden.json`.

Relevance is judged at file level: a retrieved chunk counts when its source
file is one of the labelled answers. That is coarser than passage-level
judgement and it is reproducible.

The set is split 50/50 into a dev half and a test half (`eval/split.json`,
stratified by project with a fixed seed). The one setting chosen on the data,
the per-file cap value, is chosen on the dev half only. Every table reports all
36 questions, with intervals, because 18 questions per half say little on their
own; the dev/test breakdown of the cap choice is in the
[cap table](#the-per-file-cap).

I wrote the questions and I wrote the code being searched, and there has been
one labeller. `eval/LABELLING.md` fixes the format and the procedure for a
second round with two independent labellers, an agreement statistic and an
adjudication log.

## Metrics

- **hit rate@k**: 1 when any labelled file appears in the top k chunks, else 0.
  The first version of this project called this recall@k.
- **recall@k**: the share of the labelled files that appear in the top k
  chunks. A question with four answer files and one of them in the top 5 has a
  hit rate of 1 and a recall of 0.25.
- **MRR**: one over the rank of the first relevant chunk, averaged.
- **nDCG@10**: discounted gain with one binary gain per relevant file at the
  rank of its first chunk, normalised by the ideal ordering of the labelled set.

Every cell carries a 95% percentile bootstrap interval over questions (10,000
resamples, fixed seed). Every "A beat B" statement rests on a paired bootstrap
of the per-question differences plus an exact sign test on the questions where
A and B differ. When the interval includes zero, the text says "within noise".

All three chunkers pack chunks to the same token budget, so this compares
where the boundaries fall, not how big the chunks are. Merged structural chunks
score a little higher than windows on every metric with hybrid retrieval, and
every one of those differences is within noise: on hit rate@1 only three

chunking is slightly behind the merged one, also within noise. The data does
not show that declaration boundaries beat windows on this question set.

### Hybrid against dense and BM25

Hybrid retrieval and dense retrieval alone are within noise of each other on
every metric. Dense retrieval has the higher hit rate@5 (five questions lose a
top-5 hit when the BM25 ranking is fused in, one gains one), and hybrid has the
higher hit rate@1 and MRR by amounts the intervals do not separate from zero.
Hybrid beats BM25 alone on MRR by a margin whose interval excludes zero. BM25 is
weaker than either, but less weak than in the first version of this project:
its MRR on the merged chunking is 0.34 against 0.26 before. The tokeniser
(stopwords dropped, stemming added) is the main change on that path, but the
corpus and the chunk sizes changed as well, so the two numbers are not a clean
comparison.

The cap keeps the first chunk of every file at the head of the list and pushes
the rest below every survivor, so nothing is discarded. Under file-level
relevance it cannot lower hit rate or MRR (the first chunk of a file only ever
moves up); the metric it can lower is recall@5, when the second chunk of the
right file was the one that counted. It did not: recall@5 rose from 0.57 to
0.65 with an interval that excludes zero, and MRR and nDCG@10 rose with
intervals that exclude zero. The value 1 was chosen on the dev half; the test
half agrees on direction.

Reranking the top 30 with `cross-encoder/ms-marco-MiniLM-L-6-v2` was run two
ways: on the chunk text alone, and on the same `path :: name` payload the
embedder sees, so the reranker is not judged on less information than the first

the prefixed variant is still below plain hybrid retrieval, within noise. On
window chunks both variants are below hybrid retrieval, within noise, and the
prefix makes no difference.

cell it is worse by more than the noise. It does not support a cause. Whether
the model's training domain, the 30-candidate pool or the file-level judgement
explains it was not tested.

configuration are in `results/retrievals.json`.

## How it works

```
files ──► chunker ──┬─► BM25 index          ┐
                    └─► MiniLM embeddings   ├─► RRF fusion ─► per-file cap ─► top k
                                            ┘
```

**Chunking.** Tree-sitter parses Python and Java. A class becomes a header
chunk (signature, fields, docstring) plus one chunk per method, so no line is
indexed twice; imports, module constants and a `__main__` block become
module-level chunks; comments and decorators directly above a declaration
belong to it. Markdown splits on headings and carries the heading path into the
chunk text. Files without a grammar use windows in every chunking.

**Chunk size.** `sentence-transformers/all-MiniLM-L6-v2` reads at most 256
word pieces. Every chunk is sized so that the `path :: name` prefix plus the
text fits in 254 tokens, measured with the model's own tokenizer, and the
evaluator checks every payload against the budget before embedding. A
declaration longer than that is split into consecutive parts named
`name (2/3)`. The merged chunking packs a file's units greedily to the same
budget; the window baseline packs lines to it with a quarter of each window
repeated in the next.

**Tokenisation for BM25** splits identifiers (`RateLimitFilter` is reachable
from "rate limit"), drops English stopwords and stems with Snowball.

**Fusion** is Reciprocal Rank Fusion with k = 60 over the top 60 of each list.
BM25 scores and cosine similarities are not on one scale, and a weighted blend
would add a knob that cannot be tuned honestly on 36 questions.

**Embeddings** prefix the file path and declaration name onto the chunk text
before encoding. The embedding cache is keyed on a hash of the payloads and the
model revision, so a changed corpus never reuses a stale cache.

**The per-file cap** lives in the retriever (`Index.search(..., "hybrid+cap")`),
so the configuration that ships is the one that was evaluated.

## Changes from the first published version

The first version (commit `d95035a`) reported hit rate@5 0.86 and MRR 0.591
under the name recall@5, on an unpinned corpus that included an uncommitted
working tree. This version changes the measurement, so the numbers moved:

- `recall@k` renamed to `hit_rate@k`; file-level `recall@k` added.
- nDCG@10 normalised by the labelled set with one gain per file (the old
  version normalised by the retrieved list and credited repeated chunks).
- Java methods named from the grammar's `name` field (a third of them were
  named after their return type).
- Chunks sized to the embedder window (most chunks were silently truncated).
- Class chunks no longer duplicate their methods; merged chunks are exact
  source spans.
- Stopword removal and stemming in the BM25 tokeniser.
- The per-file cap pushes overflow below the survivors instead of dropping it,
  and lives in the retriever.
- The reranker gets the same prefix as the embedder in a second variant.
- Corpus pinned to public commits; every number carries an interval.

## Limitations

- **36 questions.** The intervals are the honest width: the headline hit
  rate@5 sits in roughly 0.67 to 0.92. Most differences between configurations
  are inside that width, and the text above says so where it applies.
- **One labeller, who also wrote the code.** The second round in
  `eval/LABELLING.md` (two labellers, Cohen's kappa, adjudication log) is not
  done.
- **File-level relevance is generous.** A chunk from the right file counts even
  if it is the wrong function in that file.
- **Small dev/test halves.** The cap value was chosen on 18 questions.
- **Retrieval only.** No generation, so no faithfulness measurement.
- **Same machine, same numbers.** Two runs on one machine reproduce every
  file in `results/` byte for byte; only the timestamp, run time and commit
  hash recorded in `metadata.json` change (`codeatlas digest` hashes the files
  without those fields). Across CPUs, near-tied cosine scores can order
  differently.
